# 📂 01. 기획

## 1. 프로젝트 개요

데스크펫은 사용자의 업무 및 일정 관리를 보조하는 AI 기반 데스크 로봇이다.
> 단순한 음성 장난감이 아니라, 실제 업무 상태를 조회·변경하는 대화형 물리 인터페이스 구현

### 1-1. 개발 동기

**업무 알림 분산**

일정과 할 일이 여러 화면에 흩어져 마감을 놓치기 쉽습니다.

**수동 확인의 한계**

사용자가 앱을 열어야만 업무 상태를 확인할 수 있습니다.

**딱딱한 업무 UX**

기존 알림은 폐쇄적이며 완료·연기 처리까지 자연스럽게 이어지지 않습니다.

### 1-2. 생성형 AI 음성챗봇과의 차별점

| 요소 | 일반 음성챗 (생성형 AI + MCP) | 데스크펫 |
| --- | --- | --- |
| 대화 반응 | O | O |
| 선제적 행동 | X — 사용자가 항상 먼저 말 걸어야 함 | O — 마감 임박 시 스스로 알림 |
| 물리적 상시 존재감 | X — 앱을 켜야 함 | O — 책상 위 상시 LED 상태 표시 |
| 디바이스 간 동기화 | X — 단일 세션 안에서만 작동 | O — 팀원 펫 간 실시간 알림 전파 |
| 손을 안 쓰는 인터랙션 | 앱 실행 필요 | 버튼 하나로 즉시 인터랙션 |

**핵심 메시지**

일반 음성 챗봇은 사용자가 먼저 물어봐야 반응하는 구조입니다. 반면 데스크펫은 Eureka Process 데이터를 상시 모니터링하다가 사용자가 요청하지 않아도 먼저 알려주는 능동형 인터페이스입니다. 물리적으로 항상 켜져 있어 앱을 열지 않아도 상태를 인지할 수 있고, 여러 디바이스가 서로 연동되어 팀 단위 알림 전파가 가능합니다.

### 1-3. 로드맵

| 단계 | 일정 | 핵심 목표 | 산출물·검증 포인트 |
| --- | --- | --- | --- |
| 1차 | 9월 | 음성 명령·업무 시나리오·MVP 범위 정의 | 핵심 발화 목록, 3개 시나리오, MVP 기능 범위 |
| 2차 | 10월 | STT·TTS 및 Process API 연동 프로토타입 | 음성 입력부터 업무 CRUD까지의 프로토타입 |
| 3차 | 11월 | Raspberry Pi·버튼·LED 통합 및 리마인드 구현 | 물리 디바이스 통합, 선제 알림 동작 |
| 4차 | 12월 | 소음·오인식 테스트·전시 데모·최종 발표 | 안정화 결과, 전시 데모, 최종 발표 자료 |

**발표 시 강조할 차별화 포인트**

음성으로 업무를 처리하는 것을 넘어, 업무 데이터와 물리 디바이스를 연결해 **사용자가 묻기 전에 먼저 알려주는 팀 단위 업무관리 인터페이스**를 구현합니다.

## 2. 핵심 기능

### (1) 업무 관리

사용자는 데스크펫을 통해 업무를 등록하고 현재 업무 목록과 상태를 확인할 수 있다.

주요 기능은 다음과 같다.
- 업무 등록

- 업무 목록 조회

- 업무 상태 확인

- 업무 완료 처리

- 마감 기한 수정

업무 데이터는 외부 업무 관리 시스템인 Eureka Process와 연동하여 관리한다.

### (2) 마감 임박 알림

등록된 업무의 마감 시간이 가까워지면 데스크펫이 사용자에게 능동적으로 알림을 제공한다.

사용자가 별도의 알림 시점을 지정하지 않은 경우 기본적으로 **마감 1시간 전**에 알림을 제공한다.

알림은 다음 형태로 제공할 수 있다.
- 음성 안내

- LCD 텍스트 및 표정

- LED 색상 및 점멸

### (3) 음성 상호작용

사용자는 Push-to-Talk 방식으로 데스크펫에게 음성 명령을 전달할 수 있다.

데스크펫은 사용자의 음성을 텍스트로 변환하고, 요청 내용을 분석한 뒤 적절한 응답 또는 업무 처리를 수행한다.

주요 사용 예시는 다음과 같다.
- “내일 오후 3시까지 보고서 작성 추가해줘.”

- “오늘 마감인 업무 알려줘.”

- “보고서 작성 완료했어.”

- “마감 시간을 두 시간 미뤄줘.”

### (4) LLM 기반 응답

단순하고 명확한 사용자 요청은 경량 Intent 모델을 통해 우선 분류한다.

여러 기능이 포함되거나 문맥 해석이 필요한 복합 요청은 LLM을 통해 처리한다.

LLM은 사용자 요청 내용과 현재 업무 상태, 필요한 경우 과거 맥락을 참고하여 적절한 응답을 생성한다.

실제 업무 데이터의 조회·등록·수정은 Backend 및 Eureka Process를 통해 수행한다.

## 3. 대표 사용자 시나리오 정의

### 3-1. 대표 시나리오

**: 사용자 지정 마감 알림**

데스크펫 로봇은 사용자가 등록한 업무의 마감 기한을 관리하고, 사용자가 지정한 시점에 마감 임박 알림을 능동적으로 제공한다.
- **누가:** 팀원 박시현

- **언제·어디서:** 오후 4시, 마감 1시간 전

- **상황:** 사용자가 요청하지 않아도 서버가 Eureka Process 마감 데이터를 상시 모니터링

- **데스크펫 기능:** 임계치 도달 시 능동적으로 알림 트리거

- **Eureka Process 상태 변화:** 상태는 “진행 중” 유지, 알림 발송 이력 기록

- **사용자 반응:** LED 노란색 점멸 + TTS 선제 안내 — “보고서 검토 마감이 1시간 남았어요”

무명, 마감 기한, 우선순위 및 진행 상태와 같은 기본 업무 정보는 **Eureka Process**에서 관리한다. 업무와 관련된 메모, 과거 맥락, 사용자별 알림 설정 및 알림 처리 이력은 **Second Brain 또는 백엔드 저장소**에서 관리한다.

사용자는 업무 등록 시 원하는 마감 알림 시점을 지정할 수 있다. 별도의 알림 시점을 지정하지 않은 경우에는 **기본값으로 마감 1시간 전**을 적용한다.

Eureka Process는 마감 임박 이벤트를 직접 전송하는 Push/Webhook 기능을 제공하지 않으므로, 백엔드 서버가 일정 주기로 업무 목록을 조회(Polling)하고 마감 기한과 알림 설정을 비교하여 알림 발생 여부를 판단한다.

### 3-2. MVP 범위
- **백엔드 Polling**
  - Eureka Process의 업무 목록 및 마감 데이터를 주기적으로 조회

  - 업무 상태와 `dueAt`을 기준으로 마감 임박 여부 확인

- **능동형 WebSocket 알림**
  - 설정된 알림 시점에 도달하면 Backend에서 `proactive_alert` 이벤트 생성

  - WebSocket을 통해 Raspberry Pi에 실시간 알림 이벤트 전달

- **Eureka Process 연동**
  - 업무 상태 및 마감 정보 조회

  - 알림 발생 시에도 업무 상태는 기존 `진행 중` 상태 유지

  - 완료된 업무는 알림 대상에서 제외

- **알림 이력 관리**
  - Backend DB 또는 Second Brain에 알림 발송 이력 저장

  - 동일한 알림이 중복 발생하지 않도록 관리

- **멀티모달 출력**
  - LED 링: 알림 상태에 맞는 색상 및 점멸 출력

  - LCD: 마감 임박 표정 및 텍스트 출력

  - TTS: 마감까지 남은 시간을 음성으로 안내

### 3-3. 구현 구조

Backend Monitoring → Eureka Process → Alert Trigger → WebSocket → Raspberry Pi → LED/LCD/TTS

### 3-4. 정상흐름

**① 사용자 입력**

사용자: “9월 27일 오후 3시까지 보고서 검토해야 해. 마감 2시간 전에 알려줘.”

**② 시스템 처리 과정**
- 사용자가 Push-to-Talk 버튼을 누르고 음성 명령을 입력한다.

- 데스크펫이 음성 데이터를 백엔드 서버로 전달한다.

- STT가 음성을 텍스트로 변환한다.

- STT 결과를 경량 Intent 모델에 전달하여 요청 유형을 우선 분류한다.

- 단순 요청은 Intent 분류 결과에 따라 처리하고, 복합 요청이거나 추가적인 문맥 해석이 필요한 경우 LLM으로 전달한다.

- 시스템이 요청에서 필요한 정보를 추출한다.
  - 업무명: 보고서 검토

  - 마감 기한: 9월 27일 오후 3시

  - 알림 시점: 마감 2시간 전

- 백엔드가 Eureka Process API를 호출하여 업무를 등록한다.

- Eureka Process에서 반환된 `itemId`와 함께 사용자 지정 알림 설정을 Second Brain 또는 백엔드 저장소에 기록한다.

- 백엔드 Scheduler가 Eureka Process의 업무 목록을 주기적으로 조회한다.

- 9월 27일 오후 1시가 되면 백엔드는 해당 업무의 현재 진행 상태와 마감 기한을 확인한다.

- 업무가 완료되지 않은 상태이면 마감 알림 이벤트를 생성한다.

- 백엔드가 WebSocket을 통해 데스크펫에 `proactive_alert` 이벤트를 전달한다.

- 데스크펫이 이벤트를 수신한다.

- LED를 알림 상태로 변경하고 LCD에 마감 임박 표정 및 안내 텍스트를 표시한다.

- TTS를 통해 마감까지 남은 시간을 안내한다.

- 안내가 끝나면 데스크펫은 대기 상태로 복귀한다.

- 백엔드는 해당 알림이 전달되었음을 기록하여 동일한 알림이 중복 발생하지 않도록 한다.

**③ 최종 출력**

LED: 노란색 점멸 → 초록색 점등

LCD: 마감 임박을 나타내는 표정 및 텍스트 출력

음성 안내: “보고서 검토 마감이 2시간 남았습니다.”

**④ 성공 조건**
- 음성 명령에서 업무명, 마감 기한, 알림 시점을 정상적으로 추출한다.

- Eureka Process에 업무가 정상 등록된다.

- 사용자 지정 알림 설정이 해당 `itemId`와 연결되어 저장된다.

- 지정한 알림 시점에 미완료 업무를 정확히 탐지한다.

- 별도의 사용자 요청 없이 능동 알림이 발생한다.

- 동일한 알림이 중복 발생하지 않는다.

- 음성 안내 종료 후 데스크펫이 정상적인 대기 상태로 복귀한다.

### 3-5. 대표 시나리오 예외상황

#### (1) 사용자가 이미 업무를 완료한 경우

**① 사용자 입력**

사용자: “보고서 검토 완료했어.”

**② 시스템 처리 과정**
- 데스크펫이 사용자의 음성 명령을 수신한다.

- STT가 음성을 텍스트로 변환한다.

- 시스템이 요청을 `업무 완료` 명령으로 분류한다.

- 대상 업무인 ‘보고서 검토’를 식별한다.

- 백엔드가 Eureka Process의 업무 완료 API를 호출한다.

- Eureka Process에서 해당 업무의 모든 미완료 Stage가 `done` 상태로 변경된다.

- 백엔드는 업무 완료 성공 여부를 확인한다.

- 이후 기존에 설정된 알림 시점에 도달하더라도 Scheduler가 Eureka Process의 업무 상태를 다시 확인한다.

- 해당 업무가 `done` 상태이므로 알림 이벤트를 생성하지 않는다.

**③ 최종 출력**

업무 완료 직후:

“보고서 검토 업무를 완료 처리했어요.”

기존에 설정된 마감 알림 시점:

알림 없음

**④ 성공 조건**
- 사용자의 업무 완료 요청이 Eureka Process에 정상적으로 반영된다.

- 완료된 업무는 마감 임박 알림 대상에서 제외된다.

- 이미 완료한 업무에 대해 불필요한 알림이 발생하지 않는다.

#### (2) 네트워크 연결 실패

**① 사용자 입력**

별도의 사용자 입력은 없다.

사용자가 지정한 알림 시점에 데스크펫과 백엔드 사이의 네트워크 연결이 끊어진 상황이다.

**② 시스템 처리 과정**
- 백엔드 Scheduler가 알림 시점에 도달한 업무를 감지한다.

- Eureka Process에서 해당 업무의 최신 진행 상태를 확인한다.

- 업무가 미완료 상태이면 마감 알림 이벤트를 생성한다.

- 백엔드가 데스크펫으로 이벤트 전송을 시도한다.

- 네트워크 오류로 전달에 실패하면 해당 이벤트를 `미전달` 상태로 저장한다.

- 데스크펫은 네트워크 연결 상태를 지속적으로 확인한다.

- 연결이 복구되면 데스크펫이 백엔드와 다시 연결한다.

- 백엔드는 미전달 알림이 존재하는지 확인한다.

- 알림을 다시 보내기 전에 Eureka Process에서 업무의 최신 상태와 마감 기한을 재확인한다.

- 업무가 여전히 미완료이고 마감 전이라면 현재 남은 시간을 다시 계산한다.

- 최신 남은 시간을 반영한 알림을 데스크펫으로 전달한다.

- 전달이 완료되면 미전달 상태를 해제한다.

**③ 최종 출력**

예를 들어 마감 2시간 전에 알림이 발생했으나 네트워크 오류로 전달되지 못하고, 마감까지 1시간 30분 남았을 때 연결이 복구된 경우 다음과 같이 안내한다.

LED : 파란색 점멸

LCD : 마감 임박 표정

음성 안내: “보고서 검토 마감이 1시간 30분 남았습니다.”

**④ 성공 조건**
- 네트워크 오류로 전달되지 못한 알림 정보가 서버에 보존된다.

- 네트워크 복구 후 미전달 알림을 다시 확인한다.

- 실제 남은 시간을 기준으로 정확한 정보를 안내한다.

- 이미 완료된 업무에 대해서는 알림을 출력하지 않는다.

#### (3) 사용자가 알림 시간을 변경한 경우

**① 사용자 입력**

사용자: “보고서 검토 마감 알림 2시간 전 말고 30분 전으로 바꿔줘.”

**② 시스템 처리 과정**
- 데스크펫이 음성 명령을 수신한다.

- STT가 음성을 텍스트로 변환한다.

- 시스템이 요청을 `알림 설정 변경`으로 분류한다.

- ‘보고서 검토’ 업무를 식별한다.

- Second Brain 또는 백엔드 저장소에서 해당 업무에 연결된 기존 알림 설정을 조회한다.

- 기존 `2시간 전` 설정을 `30분 전`으로 변경한다.

- 새로운 마감 알림 예정 시간을 계산한다.

- 기존 알림 예정 정보는 무효화하고 변경된 설정을 저장한다.

- Scheduler는 이후 변경된 알림 시점을 기준으로 알림 여부를 판단한다.

- 마감 30분 전에 업무가 미완료 상태라면 새로운 알림 이벤트를 생성한다.

**③ 최종 출력**

알림 변경 요청 시 음성 안내: “보고서 검토 마감 알림을 30분 전으로 변경했어요!”

마감 30분 전 음성 안내: “보고서 검토 마감이 30분 남았습니다.”

**④ 성공 조건**
- 변경 대상 업무를 정확히 식별한다.

- 변경된 알림 시간이 정상 저장된다.

- 이전 알림 설정은 더 이상 사용되지 않는다.

- 기존 알림 시점인 마감 2시간 전에 알림이 발생하지 않는다.

- 새로운 알림 시점인 마감 30분 전에 정상적으로 알림이 발생한다.

#### (4) 사용자의 요청이 불분명한 경우

**① 사용자 입력**

사용자: “보고서 알림 설정해줘.”

**② 시스템 처리 과정**
- 데스크펫이 음성 명령을 수신하고 STT를 수행한다.

- 시스템이 요청을 `알림 설정`으로 분류한다.

- 시스템이 요청 실행에 필요한 정보를 확인한다.

- ‘보고서’라는 이름과 유사한 업무가 여러 개 존재하거나 대상 업무를 특정할 수 없는 경우 즉시 실행하지 않는다.

- 사용자에게 대상 업무 확인을 요청한다. ex) “어떤 보고서를 말씀하시는 건가요? ‘캡스톤 보고서’와 ‘클라우드 보고서’가 있어요.”

- 사용자가 대상 업무를 선택하면 알림 시점이 지정되었는지 확인한다.

- 사용자가 알림 시점을 말하지 않았다면 프로젝트 정책에 따라 **기본값인 마감 1시간 전**을 적용한다.

- 적용 전에 필요한 경우 사용자에게 설정 내용을 안내한다.

- 설정이 확정되면 해당 업무의 알림 정보를 저장한다.

**③ 최종 출력**

대상 업무를 특정할 수 없는 경우:

“어떤 보고서를 말씀하시는 건가요? ‘캡스톤 보고서’와 ‘클라우드 보고서’가 있어요.”

대상이 확인되고 알림 시간을 지정하지 않은 경우:

“캡스톤 보고서 마감 1시간 전에 알려드릴게요.”

**④ 성공 조건**
- 대상 업무를 확정할 수 없는 상태에서 임의의 업무를 변경하지 않는다.

- 필요한 정보가 부족한 경우 사용자에게 재질문한다.

- 사용자의 추가 답변을 기존 요청의 맥락과 연결한다.

- 알림 시점이 지정되지 않은 경우 기본값을 일관되게 적용한다.

- 최종적으로 확정된 업무에만 설정을 반영한다.

### 4-2. 구현 범위

#### (1) 입력 및 AI 처리
- Push-to-Talk 기반 음성 입력

- STT를 통한 음성 → 텍스트 변환

- 경량 Intent 모델 기반 단순 요청 분류

- LLM 기반 복합 요청 및 자연어 문맥 해석

- Intent 분류 결과에 따른 Backend 기능 호출

- 경량 모델에서 처리하기 어려운 요청의 LLM 전달

#### (2) 업무 관리
- 업무 등록

- 업무 목록 조회

- 업무 완료 처리

- 업무 진행 상태 조회

- 업무 마감 기한 변경 및 연기

#### (3) 마감 알림
- 사용자 지정 마감 알림

- 알림 시점 미지정 시 기본 마감 1시간 전 알림

- Scheduler / Polling 기반 마감 임박 업무 확인

- 완료된 업무의 알림 제외

- Backend에서 능동 알림 이벤트 생성

#### (4) 데스크펫 출력
- TTS 음성 출력

- LED 상태 출력

- LCD 표정 및 텍스트 출력

#### (5) 외부 시스템 및 Backend 연동
- Eureka Process API 연동

- Backend API와 Raspberry Pi 간 요청·응답 처리

- WebSocket 기반 능동 알림 전달

- 네트워크 오류 처리

- API Timeout 및 외부 API 요청 실패 처리

#### (6) 구현 제외 범위

본 프로젝트의 핵심 기능 구현과 직접적인 관련성이 낮거나 개발 기간 및 복잡도를 고려하여 다음 기능은 현재 구현 범위에서 제외한다.
- 사용자 행동 패턴 학습

- 사용자별 장기 개인화 모델

- AI 기반 업무 우선순위 자동 추천

- AI 기반 일정 자동 생성 및 재배치

- 이메일, 캘린더 등 추가 외부 서비스 연동

- 여러 업무 시스템을 동시에 연동하는 통합 업무 관리

- 완전한 오프라인 AI 처리

- 다중 사용자 계정 및 권한 관리

- 모바일 앱 또는 웹 대시보드 구현

→ **사용자가 음성으로 업무를 관리하고, 등록된 업무의 마감 시간이 가까워지면 데스크펫이 먼저 사용자에게 알려주는 기능까지**를 핵심 구현 범위로 정의한다.

Second Brain을 활용한 장기 기억 및 사용자 맥락 관리 기능은 향후 확장 가능 기능으로 분류한다.

### 4-3. 정책 문서

#### (1) 사용자 명령 처리 정책
- 명확한 요청 : 추가 질문 없이 실행

- 불명확한 요청 : 정보(업무 대상, 날짜, 시간 등)가 부족할 경우 임의의 값을 생성하지 않고, 재질문하도록 함. 업무 대상은 명확하지만 알림 시점이 지정되지 않은 경우에는 기본 정책인 마감 1시간 전을 적용한다.

#### (2) 사용자 확인 정책

업무 대상이 하나로 특정되지 않는 경우, 마감 날짜 해석이 여러 가지 가능한 경우, 기존 데이터의 중요한 값을 크게 변경하는 경우에는 추가 질문을 통해 의도를 확인한다.

반면 대상과 변경 내용이 명확한 일반 업무 등록·완료·연기 명령은 매번 별도 확인을 요구하지 않고 실행 후 결과를 안내한다.

#### (3) 실행 성공 및 실패 안내 정책

시스템은 실제 외부 시스템의 처리 성공 여부를 확인하기 전에 성공했다고 안내하지 않는다.

#### (4) Fallback 정책

STT가 실패하면 음성 재입력을 요청한다.

경량 모델이 Intent를 확정하지 못하면 LLM으로 전달한다.

LLM이 요청을 확정하지 못하면 사용자에게 필요한 정보를 재질문한다.

MCP 또는 Eureka Process 호출이 실패하면 실제 데이터 변경이 완료된 것으로 간주하지 않는다.

네트워크 장애로 능동 알림을 전달하지 못한 경우 미전달 상태로 저장하고, 연결 복구 후 업무의 최신 상태를 확인한 뒤 필요할 때만 다시 전달한다.

#### (5) 로컬 / 클라우드 처리 정책

Raspberry Pi 또는 로컬 환경에서 처리한다.
- Push-to-Talk 상태

- 경량 Intent 처리 가능한 경우

#### (7) 마감 알림 정책

사용자가 알림 시간을 지정하지 않은 경우 **마감 1시간 전**을 기본값으로 사용한다.
