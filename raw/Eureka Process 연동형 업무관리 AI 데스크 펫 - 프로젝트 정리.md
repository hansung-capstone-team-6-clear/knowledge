## 3. 개발 동기

**업무 알림 분산**

**수동 확인의 한계**

사용자가 앱을 열어야만 업무 상태를 확인할 수 있습니다.

**딱딱한 업무 UX**

기존 알림은 폐쇄적이며 완료·연기 처리까지 자연스럽게 이어지지 않습니다.

## 4. 핵심 사용 시나리오

▸

### 시나리오 1 — 업무 등록·조회
- **누가:** 신입 개발자 김지훈

- **언제·어디서:** 평일 오전 9시, 자기 자리 데스크펫 앞

- **발화:** “오늘까지 API 문서 정리 업무 등록해줘” / “오늘 할 일 뭐 남았어?”

- **데스크펫 기능:** STT → NLU로 업무명·마감 파싱 → Eureka Process 등록/조회 API 호출

- **Eureka Process 상태 변화:** 신규 업무 생성, 상태 “진행 전”

- **사용자 반응:** TTS 확인 응답 + LED 점멸 + LCD 텍스트 표시

▸

### 시나리오 2 — 팀원 간 업무 위임
- **누가:** 팀 리더 김리윤 → 팀원 박시현

- **언제·어디서:** 오후 2시, 각자 자리의 서로 다른 데스크펫

- **발화:** “경쟁사 분석 자료 조사, 시현이한테 넘겨줘. 오늘 5시까지”

- **데스크펫 기능:** 담당자·업무·마감 파싱 → Eureka Process에 업무 생성 및 담당자 지정 → 상대방 디바이스에 실시간 푸시

- **Eureka Process 상태 변화:** 시현 계정으로 업무 생성, “배정됨” → 확인 시 “확인됨”

- **사용자 반응:** 시현 펫 LED·음성 알림, 확인 후 리윤 펫에도 역알림

▸

### 시나리오 3 — 마감 임박 선제 알림 (최종 시나리오)
- **누가:** 팀원 박시현

- **언제·어디서:** 오후 4시, 마감 1시간 전

- **상황:** 사용자가 요청하지 않아도 서버가 Eureka Process 마감 데이터를 상시 모니터링

- **데스크펫 기능:** 임계치 도달 시 능동적으로 알림 트리거

- **Eureka Process 상태 변화:** 상태는 “진행 중” 유지, 알림 발송 이력 기록

- **사용자 반응:** LED 노란색 점멸 + TTS 선제 안내 — “보고서 검토 마감이 1시간 남았어요”

▸

### 시나리오 4 — 다음 일정 확인 후 이동
- **누가·언제·어디서:** 박시현, 오전 10시 45분, 외근 나가기 직전 자기 자리

- **상황:** 오전 11시 A사 미팅이 예정되어 있고, 미팅 장소인 강남까지 차로 약 20분 소요

- **발화:** “다음 일정 뭐야?”

- **데스크펫 기능:** Eureka Process에서 현재 시각 기준 가장 가까운 예정 업무·일정을 조회하고, 이동 소요시간 정보가 있으면 도착 가능 여부를 함께 계산

- **조회 결과:** 11시 A사 미팅, 장소 강남, 이동시간 약 20분

- **여유 있는 경우:** TTS로 “다음 일정은 11시 A사 미팅이에요. 강남까지 차로 20분 걸리니까 지금 출발하면 여유 있게 도착해요.”라고 안내

- **사용자 반응:** LCD에 일정명·시간·장소 표시, LED 파란색 짧은 점멸로 “확인 완료” 표시

- **시간이 빠듯한 경우:** 남은 시간이 15분인데 도착까지 20분이 걸리는 등 여유가 부족하면 LED가 주황색으로 바뀌고, “서둘러야 할 것 같아요, 이동시간이 빠듯해요”처럼 경고성 톤으로 안내

## 5. 생성형 AI 음성챗봇과의 차별점

| 요소 | 일반 음성챗 (생성형 AI + MCP) | 데스크펫 |
| --- | --- | --- |
| 대화 반응 | O | O |
| 선제적 행동 | X — 사용자가 항상 먼저 말 걸어야 함 | O — 마감 임박 시 스스로 알림 |
| 물리적 상시 존재감 | X — 앱을 켜야 함 | O — 책상 위 상시 LED 상태 표시 |
| 디바이스 간 동기화 | X — 단일 세션 안에서만 작동 | O — 팀원 펫 간 실시간 알림 전파 |
| 손을 안 쓰는 인터랙션 | 앱 실행 필요 | 버튼 하나로 즉시 인터랙션 |

**핵심 메시지**

일반 음성 챗봇은 사용자가 먼저 물어봐야 반응하는 구조입니다. 반면 데스크펫은 Eureka Process 데이터를 상시 모니터링하다가 사용자가 요청하지 않아도 먼저 알려주는 능동형 인터페이스입니다. 물리적으로 항상 켜져 있어 앱을 열지 않아도 상태를 인지할 수 있고, 여러 디바이스가 서로 연동되어 팀 단위 알림 전파가 가능합니다.

#### 대표 시나리오 : 사용자 지정 마감 알림

데스크펫 로봇은 사용자가 등록한 업무의 마감 기한을 관리하고, 사용자가 지정한 시점에 마감 임박 알림을 능동적으로 제공한다.

무명, 마감 기한, 우선순위 및 진행 상태와 같은 기본 업무 정보는 **Eureka Process**에서 관리한다. 업무와 관련된 메모, 과거 맥락, 사용자별 알림 설정 및 알림 처리 이력은 **Second Brain 또는 백엔드 저장소**에서 관리한다.

사용자는 업무 등록 시 원하는 마감 알림 시점을 지정할 수 있다. 별도의 알림 시점을 지정하지 않은 경우에는 **기본값으로 마감 1시간 전**을 적용한다.

Eureka Process는 마감 임박 이벤트를 직접 전송하는 Push/Webhook 기능을 제공하지 않으므로, 백엔드 서버가 일정 주기로 업무 목록을 조회(Polling)하고 마감 기한과 알림 설정을 비교하여 알림 발생 여부를 판단한다.

▸

#### 정상 흐름

**① 사용자 입력**

사용자: “9월 27일 오후 3시까지 보고서 검토해야 해. 마감 2시간 전에 알려줘.”

**② 시스템 처리 과정**

1. 사용자가 Push-to-Talk 버튼을 누르고 음성 명령을 입력한다.
2. 데스크펫이 음성 데이터를 백엔드 서버로 전달한다.
3. STT가 음성을 텍스트로 변환한다.
4. 경량 Intent 분류 또는 LLM이 요청을 `업무 등록`으로 판단한다.
5. 시스템이 다음 정보를 추출한다.
- 업무명: 보고서 검토
- 마감 기한: 9월 27일 오후 3시
- 알림 시점: 마감 2시간 전
6. 백엔드가 Eureka Process API를 호출하여 업무를 등록한다.
7. Eureka Process에서 반환된 `itemId`와 함께 사용자 지정 알림 설정을 Second Brain 또는 백엔드 저장소에 기록한다.
8. 백엔드 Scheduler가 Eureka Process의 업무 목록을 주기적으로 조회한다.
9. 9월 27일 오후 1시가 되면 백엔드는 해당 업무의 현재 진행 상태와 마감 기한을 확인한다.
10. 업무가 완료되지 않은 상태이면 마감 알림 이벤트를 생성한다.
11. 데스크펫이 이벤트를 수신한다.
12. LED를 응답 상태로 변경하고 LCD에 마감 임박 표정을 표시한다.
13. TTS를 통해 마감까지 남은 시간을 안내한다.
14. 안내가 끝나면 데스크펫은 대기 상태로 복귀한다.
15. 백엔드는 해당 알림이 전달되었음을 기록하여 동일한 알림이 중복 발생하지 않도록 한다.

**③ 최종 출력**

LED: 파란색 점멸 → 초록색 점등

LCD: 마감 임박을 나타내는 표정

음성 안내: “보고서 검토 마감이 2시간 남았습니다.”

**④ 성공 조건**

- 음성 명령에서 업무명, 마감 기한, 알림 시점을 정상적으로 추출한다.
- Eureka Process에 업무가 정상 등록된다.
- 사용자 지정 알림 설정이 해당 `itemId`와 연결되어 저장된다.
- 지정한 알림 시점에 미완료 업무를 정확히 탐지한다.
- 별도의 사용자 요청 없이 능동 알림이 발생한다.
- 동일한 알림이 중복 발생하지 않는다.
- 음성 안내 종료 후 데스크펫이 정상적인 대기 상태로 복귀한다.

#### 네트워크 연결 실패

**① 사용자 입력**

별도의 사용자 입력은 없다.

사용자가 지정한 알림 시점에 데스크펫과 백엔드 사이의 네트워크 연결이 끊어진 상황이다.

**② 시스템 처리 과정**

1. 백엔드 Scheduler가 알림 시점에 도달한 업무를 감지한다.
2. Eureka Process에서 해당 업무의 최신 진행 상태를 확인한다.
3. 업무가 미완료 상태이면 마감 알림 이벤트를 생성한다.
4. 백엔드가 데스크펫으로 이벤트 전송을 시도한다.
5. 네트워크 오류로 전달에 실패하면 해당 이벤트를 `미전달` 상태로 저장한다.
6. 데스크펫은 네트워크 연결 상태를 지속적으로 확인한다.
7. 연결이 복구되면 데스크펫이 백엔드와 다시 연결한다.
8. 백엔드는 미전달 알림이 존재하는지 확인한다.
9. 알림을 다시 보내기 전에 Eureka Process에서 업무의 최신 상태와 마감 기한을 재확인한다.
10. 업무가 여전히 미완료이고 마감 전이라면 현재 남은 시간을 다시 계산한다.
11. 최신 남은 시간을 반영한 알림을 데스크펫으로 전달한다.
12. 전달이 완료되면 미전달 상태를 해제한다.

**③ 최종 출력**

예를 들어 마감 2시간 전에 알림이 발생했으나 네트워크 오류로 전달되지 못하고, 마감까지 1시간 30분 남았을 때 연결이 복구된 경우 다음과 같이 안내한다.

LED : 파란색 점멸

LCD : 마감 임박 표정

음성 안내: “보고서 검토 마감이 1시간 30분 남았습니다.”

**④ 성공 조건**

- 네트워크 오류로 전달되지 못한 알림 정보가 서버에 보존된다.
- 네트워크 복구 후 미전달 알림을 다시 확인한다.
- 실제 남은 시간을 기준으로 정확한 정보를 안내한다.
- 이미 완료된 업무에 대해서는 알림을 출력하지 않는다.

#### 사용자가 알림 시간을 변경한 경우

**① 사용자 입력**

사용자: “보고서 검토 마감 알림 2시간 전 말고 30분 전으로 바꿔줘.”

**④ 성공 조건**

- 기존 알림 시점인 마감 2시간 전에 알림이 발생하지 않는다.
- 새로운 알림 시점인 마감 30분 전에 정상적으로 알림이 발생한다.

#### 사용자의 요청이 불분명할 경우

**① 사용자 입력**

사용자: “보고서 알림 설정해줘.”

**② 시스템 처리 과정**

1. 데스크펫이 음성 명령을 수신하고 STT를 수행한다.
2. 시스템이 요청을 `알림 설정`으로 분류한다.
3. 시스템이 요청 실행에 필요한 정보를 확인한다.
4. ‘보고서’라는 이름과 유사한 업무가 여러 개 존재하거나 대상 업무를 특정할 수 없는 경우 즉시 실행하지 않는다.
5. 사용자에게 대상 업무 확인을 요청한다. ex) “어떤 보고서를 말씀하시는 건가요? ‘캡스톤 보고서’와 ‘클라우드 보고서’가 있어요.”
6. 사용자가 대상 업무를 선택하면 알림 시점이 지정되었는지 확인한다.
7. 사용자가 알림 시점을 말하지 않았다면 프로젝트 정책에 따라 **기본값인 마감 1시간 전**을 적용한다.
8. 적용 전에 필요한 경우 사용자에게 설정 내용을 안내한다.
9. 설정이 확정되면 해당 업무의 알림 정보를 저장한다.

**③ 최종 출력**

대상 업무를 특정할 수 없는 경우:

“어떤 보고서를 말씀하시는 건가요? ‘캡스톤 보고서’와 ‘클라우드 보고서’가 있어요.”

대상이 확인되고 알림 시간을 지정하지 않은 경우:

“캡스톤 보고서 마감 1시간 전에 알려드릴게요.”

**④ 성공 조건**

- 대상 업무를 확정할 수 없는 상태에서 임의의 업무를 변경하지 않는다.
- 필요한 정보가 부족한 경우 사용자에게 재질문한다.
- 사용자의 추가 답변을 기존 요청의 맥락과 연결한다.
- 알림 시점이 지정되지 않은 경우 기본값을 일관되게 적용한다.
- 최종적으로 확정된 업무에만 설정을 반영한다.

#### Fallback 정책

STT가 실패하면 음성 재입력을 요청한다.

경량 모델이 Intent를 확정하지 못하면 LLM으로 전달한다.

LLM이 요청을 확정하지 못하면 사용자에게 필요한 정보를 재질문한다.

MCP 또는 Eureka Process 호출이 실패하면 실제 데이터 변경이 완료된 것으로 간주하지 않는다.

네트워크 장애로 능동 알림을 전달하지 못한 경우 미전달 상태로 저장하고, 연결 복구 후 업무의 최신 상태를 확인한 뒤 필요할 때만 다시 전달한다.

#### Eureka Process 관련 정책

Backend는 Eureka의 API 형식을 Raspberry Pi에 직접 노출하지 않고 내부 Adapter를 통해 호출한다.

API Key는 Raspberry Pi나 Git 저장소에 포함하지 않고 Backend의 환경변수 `.env`에서 관리한다.

또한 Eureka Process는 마감시간 범위 검색 및 Push/Webhook 방식의 알림을 제공하지 않으므로 마감 임박 판단은 Backend에서 수행한다.

사용자와 데스크펫 사이의 물리적인 입출력을 담당한다.

- Push-to-Talk 버튼 입력 감지
- 사용자 음성 녹음
- 음성 데이터 생성 및 전송
- 스피커 출력
- LED 상태 제어
- LCD 표정 및 텍스트 출력
- Wi-Fi 및 하드웨어 상태 감지

**인터페이스**

**(1) 버튼 입력 인터페이스 : IButtonInput**

입력 데이터 ㅡ 버튼 눌림 및 해제 신호

출력 데이터 ㅡ BUTTON_PRESSED, BUTTON_RELEASED

호출 방식 ㅡ Raspberry Pi GPIO 이벤트 혹은 인터럽트

처리 방식 ㅡ 비동기 이벤트 기반

오류 처리 ㅡ 짧은 시간동안 반복되는 입력은 디바운싱 처리. 입력장치 오류 발생 시 로그 기록.

Timeout 처리 ㅡ 버튼이 계속 눌린 상태로 유지되지 않도록 최대 녹음 시간 지정 → 초과 시 강제종료

**(2) 음성 입력 인터페이스 : IAudioCapture**

입력 데이터 ㅡ 녹음 시작/종료 이벤트

출력 데이터 ㅡ WAV 또는 PCM 음성 데이터, 녹음 길이, 샘플링 정보, 요청 ID

호출 방식 ㅡ Raspberry Pi 내부 오디오 장치 API

처리 방식 - 비동기

오류 처리 ㅡ 마이크 연결 실패 또는 음성 데이터 생성 실패 시 오류 상태를 반환한다.

Timeout 처리 ㅡ 초기 최대 녹음 시간은 15초로 설정한다.

**(3) 출력 장치 제어 인터페이스 : IHardwareOutput**

입력 데이터 ㅡ TTS 음성 데이터, LED 상태, LCD 표정 및 텍스트

출력 데이터 ㅡ 음성 재생 완료 여부, LED 상태 변경 결과, LCD 출력 결과

호출 방식 ㅡ Raspberry Pi 내부 장치 제어 함수 호출

처리 방식 ㅡ 비동기

오류 처리 ㅡ 특정 출력 장치에 오류가 발생해도 정상 작동하는 다른 출력 장치를 통해 가능한 범위에서 사용자에게 결과를 안내한다.

Timeout 처리 ㅡ 음성 출력이나 장치 제어가 비정상적으로 지속되면 출력을 종료하고 대기 상태로 복귀한다.

LED 상태 ㅡ `IDLE`: 초록색 / `LISTENING`: 노란색 점멸 / `SPEAKING`: 파란색 점멸

#### STT

**역할 및 책임**

사용자의 음성 데이터를 텍스트로 변환한다.

- 음성 데이터 수신
- 음성 데이터 유효성 검사
- 음성 → 텍스트 변환
- 요청 ID와 인식 결과 연결
- 무음 및 음성 인식 실패 처리

**인터페이스**

**(1) 음성 인식 인터페이스 : SpeechToText**

입력 데이터 ㅡ 음성 파일 또는 오디오 스트림, 요청 ID, 언어 설정

출력 데이터 ㅡ 인식된 텍스트, 인식 상태, 요청 ID

호출 방식 ㅡ Raspberry Pi에서 STT 처리 모듈 또는 백엔드 서버로 음성 데이터 전달

처리 방식 ㅡ 비동기

오류 처리 ㅡ 무음 입력 시 `NO_SPEECH` 상태 반환. 음성 인식 결과가 불명확하면 사용자에게 재입력을 요청한다. STT 서비스 오류 발생 시 `STT_ERROR`를 반환하고 로그를 기록한다.

Timeout 처리 ㅡ 목표 처리시간은 1초 이내로 설정하며 최대 5초를 초과하면 요청을 중단한다.

#### 경량 모델

**역할 및 책임**

STT로 변환된 사용자 텍스트의 의도를 빠르게 분류하고 LLM 호출 여부를 결정한다.

- 사용자 Intent 분류
- 단순 명령 / 복합 명령 구분
- 기본적인 명령 처리
- LLM 호출 필요 여부 판단
- 불명확한 요청 감지

**인터페이스**

**(1) Intent 분류 인터페이스 : ClassifyIntent**

입력 데이터 ㅡ 사용자 요청 텍스트, 요청 ID

출력 데이터 ㅡ Intent, Confidence, LLM 호출 필요 여부

호출 방식 ㅡ 백엔드 내부 함수 또는 경량 모델 호출

처리 방식 ㅡ 동기

오류 처리 ㅡ Intent 신뢰도가 기준 이하이거나 필요한 정보가 부족한 경우 임의로 명령을 실행하지 않고 LLM 또는 사용자 재질문 단계로 전달한다.

Timeout 처리 ㅡ 목표 처리시간은 500ms 이내, 최대 1초로 설정한다.

**(2) 단순 명령 처리 인터페이스 : HandleSimpleCommand**

입력 데이터 ㅡ Intent, 사용자 명령, 필요한 매개변수

출력 데이터 ㅡ 응답 텍스트 또는 로봇 제어 명령

호출 방식 ㅡ 백엔드 내부 함수 호출

처리 방식 ㅡ 동기

오류 처리 ㅡ 단순 명령으로 분류되었으나 외부 데이터나 추가 맥락이 필요한 경우 LLM Layer로 전달한다.

Timeout 처리 ㅡ 최대 1초 이내에 처리한다.

#### LLM/MCP

**역할 및 책임**

복합적인 자연어 요청을 분석하고 필요한 외부 기능을 결정한다.

- 복합 사용자 요청 해석
- 업무명 / 날짜 / 시간 / 우선순위 추출
- 필요한 정보의 누락 여부 판단
- 과거 맥락 활용
- MCP Tool 선택
- 외부 시스템 호출 결과 해석
- 불명확한 요청에 대한 재질문 생성

**인터페이스**

**(1) 복합 요청 분석 인터페이스 : AnalyzeUserRequest**

입력 데이터 ㅡ 사용자 요청 텍스트, 현재 날짜 및 시간, 대화 맥락

출력 데이터 ㅡ Intent, 추출된 매개변수, 필요한 Tool, 추가 질문 필요 여부

호출 방식 ㅡ 백엔드 서버에서 LLM API 호출

처리 방식 ㅡ 비동기

오류 처리 ㅡ 필수 정보가 부족한 경우 사용자에게 재질문한다. LLM이 확정할 수 없는 날짜나 업무를 임의로 생성하지 않는다.

Timeout 처리 ㅡ 최대 5초로 설정하고 초과 시 사용자에게 처리 실패를 안내한다.

**(2) 외부 도구 호출 인터페이스 : CallMCPTool**

입력 데이터 ㅡ Tool 이름, 작업 유형, 요청 매개변수, 요청 ID

출력 데이터 ㅡ Tool 실행 결과, 성공 여부, 오류 정보

호출 방식 ㅡ Backend MCP Client가 MCP Tool 호출

처리 방식 ㅡ 비동기

오류 처리 ㅡ Tool 호출 실패 시 오류 코드와 원인을 반환한다. 권한이 없는 기능은 실행하지 않으며 데이터 변경 요청은 요청 ID를 사용하여 중복 실행을 방지한다.

Timeout 처리 ㅡ Tool별 최대 3~5초로 설정한다.

#### Backend API

**역할 및 책임**

Raspberry Pi, STT, AI 모델, Eureka Process, Second Brain 사이의 요청·응답 흐름을 관리한다.

- Raspberry Pi 요청 수신
- STT / Intent / LLM 처리 흐름 관리
- Eureka Process API 호출
- Second Brain 저장 및 조회

- Scheduler / Polling 실행
- 마감 임박 이벤트 생성
- Timeout 및 오류 처리
- API Key 및 환경변수 관리
- Latency 측정 및 로그 기록

**인터페이스**

**(1) 업무 등록 인터페이스 : CreateTaskAPI**

Endpoint ㅡ `POST /api/tasks`

입력 데이터 ㅡ 요청 ID, 업무명, 마감 기한, 우선순위, 사용자 지정 알림 시간

출력 데이터 ㅡ 등록 성공 여부, Eureka itemId, 업무 상태, 사용자 안내 메시지

호출 방식 ㅡ Raspberry Pi → Backend HTTPS 요청

처리 방식 ㅡ 비동기

오류 처리 ㅡ 필수 정보가 부족하면 사용자에게 추가 입력을 요청한다. Eureka Process 업무 등록에 실패하면 실제 등록되지 않은 업무를 성공으로 안내하지 않는다.

Timeout 처리 ㅡ Backend 내부 처리는 최대 500ms를 목표로 하며 Eureka 호출을 포함한 전체 처리는 시스템 응답시간 정책을 따른다.

**(2) 업무 조회 인터페이스 : GetTasksAPI**

Endpoint ㅡ `GET /api/tasks`

입력 데이터 ㅡ 요청 ID, 조회 조건

출력 데이터 ㅡ 등록된 업무 목록, 마감 기한, 우선순위 및 상태

호출 방식 ㅡ Raspberry Pi → Backend HTTPS 요청

처리 방식 ㅡ 비동기

오류 처리 ㅡ 조회 실패 시 임의의 업무 데이터를 생성하지 않고 조회 실패 상태를 반환한다.

Timeout 처리 ㅡ 최대 5초 이내에 처리한다.

**(3) 업무 완료 인터페이스 : CompleteTaskAPI**

Endpoint ㅡ `POST /api/tasks/{itemId}/complete`

입력 데이터 ㅡ 업무 ID

출력 데이터 ㅡ 완료 처리 성공 여부, 최종 업무 상태

호출 방식 ㅡ Raspberry Pi → Backend → Eureka Process

처리 방식 ㅡ 비동기

오류 처리 ㅡ 존재하지 않는 업무이거나 대상 업무를 특정할 수 없는 경우 완료 처리하지 않고 사용자에게 확인을 요청한다.

Timeout 처리 ㅡ 최대 5초 이내에 처리한다.

**(4) 업무 상태 확인 인터페이스 : GetTaskStatusAPI**

Endpoint ㅡ `GET /api/tasks/{itemId}/status`

입력 데이터 ㅡ 업무 ID

출력 데이터 ㅡ `todo`, `doing`, `done`, `hold` 상태 및 전체/완료 Stage 수

호출 방식 ㅡ Raspberry Pi → Backend → Eureka Process

처리 방식 ㅡ 비동기

오류 처리 ㅡ 상태를 확인하지 못한 경우 기존 값을 추정하지 않고 조회 실패 상태를 반환한다.

Timeout 처리 ㅡ 최대 5초 이내에 처리한다.

**(5) 업무 수정 인터페이스 : UpdateTaskAPI**

Endpoint ㅡ `PUT /api/tasks/{itemId}`

입력 데이터 ㅡ 업무 ID, 변경할 마감 기한 / 업무명 / 우선순위

출력 데이터 ㅡ 변경 성공 여부, 변경된 업무 정보

호출 방식 ㅡ Raspberry Pi → Backend → Eureka Process

처리 방식 ㅡ 비동기

오류 처리 ㅡ 존재하지 않는 업무 또는 잘못된 입력이면 변경하지 않고 오류 상태를 반환한다.

Timeout 처리 ㅡ 최대 5초 이내에 처리한다.

#### Eureka Process

**역할 및 책임**

업무의 기준 정보를 저장하고 관리한다.

- 업무 등록
- 업무 목록 조회
- 업무 완료 처리
- 업무 진행 상태 관리
- 마감 기한 변경
- 업무명 및 우선순위 변경
- Item ID 및 Stage ID 관리

**인터페이스**

**(1) 업무 등록 인터페이스 : CreateTask**

입력 데이터 ㅡ `processId`, 업무명, `dueAt`, 우선순위

출력 데이터 ㅡ `itemId`, `stageIds`, 생성된 업무 정보

호출 방식 ㅡ `POST /_api_/items/0/start`

처리 방식 ㅡ 비동기 HTTP 요청

오류 처리 ㅡ 요청 실패 시 HTTP 상태 코드와 응답 본문을 함께 확인한다. 필수값이 누락된 경우 등록하지 않는다.

Timeout 처리 ㅡ 목표 응답시간 1초 이내, 최대 2초를 우선 기준으로 설정한다.

**(2) 업무 조회 인터페이스 : GetTasks**

입력 데이터 ㅡ Workspace 및 조회 옵션

출력 데이터 ㅡ 업무 목록 및 `stage$$`

호출 방식 ㅡ `GET /_api_/items/0/list?sites&detail=true`

처리 방식 ㅡ 비동기 HTTP 요청

오류 처리 ㅡ API 조회 실패 시 Backend에 오류 상태를 반환한다.

Timeout 처리 ㅡ 목표 응답시간 1초 이내, 최대 2초를 우선 기준으로 설정한다.

**(3) 업무 완료 인터페이스 : CompleteTask**

입력 데이터 ㅡ `itemId`

출력 데이터 ㅡ 완료 처리된 업무 및 Stage 상태

호출 방식 ㅡ `POST /_api_/items/{itemId}/complete`

처리 방식 ㅡ 비동기 HTTP 요청

오류 처리 ㅡ 업무가 `hold` 상태 등으로 인해 완료할 수 없는 경우 오류 상태를 Backend에 반환한다.

Timeout 처리 ㅡ 목표 응답시간 1초 이내, 최대 2초를 우선 기준으로 설정한다.

**(4) 업무 상태 확인 인터페이스 : GetTaskStatus**

입력 데이터 ㅡ `itemId`

출력 데이터 ㅡ 업무 상태, 전체 Stage 수, 완료 Stage 수

호출 방식 ㅡ `GET /_api_/items/{itemId}/status`

처리 방식 ㅡ 비동기 HTTP 요청

오류 처리 ㅡ 존재하지 않는 ID 또는 API 오류 시 상태 조회 실패 결과를 반환한다.

Timeout 처리 ㅡ 목표 응답시간 1초 이내, 최대 2초를 우선 기준으로 설정한다.

**(5) 업무 수정 및 연기 인터페이스 : UpdateTask**

입력 데이터 ㅡ `itemId`, 변경할 `dueAt`, 업무명 또는 우선순위

출력 데이터 ㅡ 변경된 업무 정보

호출 방식 ㅡ `PUT /_api_/items/{itemId}`

처리 방식 ㅡ 비동기 HTTP 요청

오류 처리 ㅡ 유효하지 않은 값 또는 존재하지 않는 업무 ID가 입력된 경우 변경하지 않는다.

Timeout 처리 ㅡ 목표 응답시간 1초 이내, 최대 2초를 우선 기준으로 설정한다.

#### Second Brain

**역할 및 책임**

Eureka Process에 저장되는 기본 업무 정보 외의 사용자 업무 맥락과 기록을 저장하고 검색한다.

- 업무 관련 메모 저장
- 회의 기록 저장
- 이전 작업 내용 저장
- 프로젝트별 업무 맥락 관리
- 업무와 과거 기록 연결
- 사용자 지정 마감 알림 설정 저장
- 알림 전달 이력 및 미전달 상태 관리

**인터페이스**

**(1) 업무 기록 저장 인터페이스 : SaveWorkRecord**

입력 데이터 ㅡ 업무 ID, 업무명, 업무 메모, 프로젝트 ID, 기록 일시

출력 데이터 ㅡ 저장된 기록 ID, 저장 성공 여부

Timeout 처리 ㅡ 최대 3초로 설정한다.

**(3) 과거 맥락 검색 인터페이스 : SearchContext**

호출 방식 ㅡ MCP Tool 또는 Backend 검색 서비스 호출

호출 방식 ㅡ Backend 내부 저장 서비스 호출

- PoC 과정에서 확인한 Eureka Process 제약사항

(1) 마감 기한 범위 검색 미지원

→ Backend에서 전체 업무 목록을 조회한 후 각 업무의 `dueAt`을 기준으로 직접 필터링해야 한다.

(2) Push / Webhook 미지원

→ 업무 마감 시점에 Backend 또는 데스크펫으로 이벤트를 자동 전송하는 Push/Webhook 기능을 제공하지 않는다.
따라서 Backend에서 일정 주기로 업무 목록을 조회하는 **Polling 방식**이 필요하다.

(3) 업무 상태 관리 방식

→ 업무 완료 상태는 Item 자체보다 하위 Stage의 상태를 기준으로 표현된다.
`GET /_api_/items/{itemId}/status`을 사용하고, 여러 업무를 동시에 확인하는 Polling 상황에서는 목록의 `stage$$`를 이용해 상태를 판단하는 방식이 적합하다.

(4) 오류 응답 처리

→ 입력 데이터 오류가 항상 `400 Bad Request`로 반환되는 것은 아니며 일부 검증 실패는 `500`으로 반환될 수 있다.
따라서 HTTP Status Code만 확인하지 않고 응답 Body의 오류 메시지까지 함께 확인해야 한다.

## STT vs TTS

| 구분 | STT | TTS |
| --- | --- | --- |
| 의미 | Speech-to-Text | Text-to-Speech |
| 변환 방향 | 음성 → 텍스트 | 텍스트 → 음성 |
| 역할 | AI의 **귀** | AI의 **입** |
| 기능 | 사람의 말을 문자로 변환 | 문자를 사람의 음성으로 변환 |
| 사용 예시 | 음성 검색, 자동 자막, 음성 메모 | 내비게이션, 오디오북, AI 스피커·데스크펫 음성 응답 |

**STT ➔ 백엔드·LLM ➔ TTS 전체 음성 대화 흐름**
```
[1] 라즈베리파이 Edge
    Push-to-Talk 버튼 입력
            ↓
    ICS-43434 마이크로 음성 녹음
            ↓
    PCM 오디오 데이터 생성
            ↓
    WebSocket 스트림으로 백엔드 전송
            │
            ▼ 인터넷 통신
[2] 중앙 백엔드 서버 · AI Pipeline
    Faster-Whisper(STT)
    음성 데이터를 텍스트로 변환
            ↓
    GPT-4o-mini(LLM)
    사용자 질문 분석
    필요한 경우 Eureka Process API 또는 Notion 조회
    응답 문장 생성
            ↓
    Edge-TTS
    응답 텍스트를 음성 오디오로 변환
            ↓
    PCM 또는 MP3 오디오 스트림 생성
            │
            ▼ 인터넷 통신
[3] 라즈베리파이 Edge
    백엔드에서 오디오 패킷 수신
            ↓
    MAX98357A 앰프로 음성 출력
            ↓
    LCD 표정 및 LED 색상 동기화
```

### **단계별 정리**

| **단계** | **위치** | **처리 내용** | **주요 구성 요소** |
| --- | --- | --- | --- |
| 1. 음성 입력 | 라즈베리파이 | 사용자가 버튼을 누르고 질문하면 음성을 녹음한 뒤 PCM 데이터로 생성 | Push-to-Talk, ICS-43434 |
| 2. 음성 전송 | 라즈베리파이 → 백엔드 | 오디오 데이터를 WebSocket 스트림으로 서버에 전송 | 인터넷, WebSocket |
| 3. 음성 인식 | 백엔드 | 음성을 텍스트로 변환 | Faster-Whisper, STT |
| 4. 질문 분석 | 백엔드 | 질문의 의도와 필요한 정보를 분석하고 외부 API·Notion 조회 여부를 판단 | GPT-4o-mini, LLM |
| 5. 응답 생성 | 백엔드 | 분석 결과를 바탕으로 사용자에게 전달할 응답 문장 생성 | LLM, Eureka Process API |
| 6. 음성 합성 | 백엔드 | 응답 문장을 음성 오디오로 변환 | Edge-TTS |
| 7. 음성 전송 | 백엔드 → 라즈베리파이 | 생성된 PCM 또는 MP3 오디오 스트림을 전송 | 인터넷, 오디오 패킷 |
| 8. 음성·시각 출력 | 라즈베리파이 | 스피커로 음성을 출력하고 LCD 표정과 LED 색상을 동기화 | MAX98357A, LCD, LED |

**전체 흐름:**

`사용자 음성 ➔ STT ➔ LLM·외부 API 처리 ➔ TTS ➔ 스피커·LCD·LED 출력`

### 대표 시나리오 및 MVP 구현 범위

**대표 시나리오 — 마감 임박 선제 알림**

  - LCD: 눈동자 표정 변경 — `ALERT_EYES` 및 업무명·마감 시간 표시

  - TTS: “지훈 님, 보고서 제출 마감이 1시간 남았습니다!”

- **대표 시나리오 (사용자 지정 알림 및 대화형 업무 처리):**
  - **정상 흐름:** 사용자가 "9월 27일 오후 3시까지 보고서 검토해야 해. 마감 2시간 전에 알려줘."라고 음성 명령을 내리면, AI가 발화를 분석하여 `업무명`, `마감일시`, `알림 시점(120분 전)`을 파싱 후 백엔드 및 Eureka Process 연동용 JSON을 생성합니다.

  - **기본값 적용:** 사용자가 별도의 알림 시점을 말하지 않은 경우 프로젝트 정책에 따라 기본값인 `마감 1시간 전(60분)`을 자동 적용합니다.

  - **예외/재질문 흐름:** 대상 업무가 모호한 경우("보고서 알림 설정해줘") AI가 임의로 처리하지 않고, 사용자에게 선택지를 제시하는 재질문(`need_clarification`) 문장과 표정을 생성합니다.

- **MVP 범위 (AI 파트):**
  - **2단계 의도 처리:** 경량 의도 분류(500ms 이내) 및 LLM 기반 복합 파라미터 추출 분리.

  - **구조화된 데이터 추출 (Structured Output):** NLU/LLM을 통해 업무 제어에 필요한 슬롯 데이터를 엄격한 JSON Schema로 변환.

  - **대화형 예외 처리 및 피드백 제어:** 불명확 요청 시 Clarification 수행, 처리 결과에 따른 데스크펫 피드백(TTS 문장, LED 색상, LCD 표정 ID) 동시 생성.
