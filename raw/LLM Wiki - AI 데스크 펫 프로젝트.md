- 모델, 프롬프트, 평가 결과가 바뀌면 변경 이유를 함께 남긴다.

## 2. LLM이란?

LLM(Large Language Model)은 대규모 텍스트 데이터를 학습하여 자연어를 이해하고 새로운 텍스트를 생성하는 모델이다.

우리 프로젝트에서는 LLM을 음성 자체를 처리하는 모델이 아니라, STT가 변환한 텍스트를 분석하는 **언어 이해 및 판단 계층**으로 사용한다.

### 주요 용어

| 용어 | 설명 |
| --- | --- |
| Token | 모델이 텍스트를 처리하는 기본 단위 |
| Context | 모델이 현재 응답을 만들 때 참고하는 입력 정보 |
| Prompt | 모델에게 전달하는 지시와 입력 |
| System Prompt | 모델의 역할과 행동 규칙을 정의하는 지시 |
| Temperature | 응답의 무작위성과 창의성 정도를 조절하는 값 |
| Hallucination | 근거가 부족한 내용을 사실처럼 생성하는 현상 |
| Streaming | 응답을 완성한 뒤 한 번에 보내지 않고 생성되는 즉시 전달하는 방식 |
| Tool Calling | 모델이 외부 기능이나 API를 호출하도록 요청하는 방식 |

## 3. 프로젝트 내 AI 처리 흐름
```
사용자 음성
    ↓
Push-to-Talk 버튼·마이크 입력
    ↓
STT — Faster-Whisper
    ↓
텍스트 정제 및 Intent 분류
    ↓
LLM — 복합 요청 분석·정보 추출
    ↓
MCP 또는 Eureka Process API 호출
    ↓
실행 결과 확인
    ↓
LLM 또는 Backend 응답 문장 생성
    ↓
TTS — Edge-TTS
    ↓
스피커·LCD·LED 출력
```

### 구성 요소별 역할

| 구성 요소 | 역할 |
| --- | --- |
| STT | 사용자의 음성을 텍스트로 변환 |
| 경량 Intent 분류기 | 단순 명령과 복합 명령을 구분하고 LLM 호출 여부 판단 |
| LLM | 자연어 의도 분석, 업무 정보 추출, Tool 선택, 재질문 생성 |
| MCP / Eureka API | 업무 등록·조회·완료·수정 등 실제 데이터 처리 |
| Backend | 전체 파이프라인, 세션, 오류, 인증 정보 관리 |
| TTS | 응답 텍스트를 음성으로 변환 |
| 데스크 펫 | 음성·화면·LED를 통한 사용자 피드백 |

## 4. LLM의 담당 범위

### LLM이 담당하는 일
- 복합 자연어 요청의 의도 파악

- 업무명, 날짜, 시간, 우선순위 추출

- 필요한 정보의 누락 여부 판단

- MCP Tool 또는 API 호출 필요 여부 판단

- 외부 도구 결과를 사용자용 문장으로 변환

- 요청이 불명확할 때 재질문 문장 생성

- 대화 맥락을 참고한 후속 요청 해석

### LLM이 직접 하면 안 되는 일
- 확인되지 않은 업무를 임의로 등록하거나 수정하기

- API Key 또는 인증 정보를 생성·노출하기

- 외부 API 성공 여부를 확인하지 않고 성공했다고 안내하기

- 대상 업무가 불명확한데 임의로 하나를 선택하기

- 현재 날짜와 시간이 필요한 요청에서 기준 시각 없이 날짜를 추측하기

## 5. 단순 명령과 복합 명령 분리

모든 요청을 LLM으로 처리하지 않는다. 단순하고 정해진 명령은 규칙 기반 또는 경량 모델로 처리하여 응답 시간과 비용을 줄인다.

| 분류 | 예시 | 처리 방식 |
| --- | --- | --- |
| 단순 명령 | “다시 말해줘” | 규칙 기반 |
| 단순 조회 | “현재 상태 알려줘” | 경량 분류 후 Backend 처리 |
| 업무 조회 | “오늘 할 일 뭐야?” | Intent 분류 후 API 조회 |
| 복합 등록 | “금요일 3시까지 보고서 검토하고 2시간 전에 알려줘” | LLM 정보 추출 후 API 호출 |
| 모호한 요청 | “그거 처리해줘” | LLM 또는 Backend가 재질문 |

## 6. 모델 및 실행 방식 비교

| 구분 | 후보 | 장점 | 확인할 항목 |
| --- | --- | --- | --- |
| 클라우드 LLM | GPT-4o-mini | 빠른 응답과 API 기반 사용 | 비용, 네트워크, 개인정보 |
| 클라우드 LLM | Claude | 자연어 처리 및 긴 문맥 활용 검토 | 비용, 응답 시간, API 연동 |
| 로컬 LLM | Ollama + Llama 3 8B | 로컬 실행 및 외부 전송 최소화 | Raspberry Pi 성능, 발열, 응답 지연 |
| 자체 서버 | vLLM | 모델 서버화와 동시 요청 처리 검토 | GPU 자원, 운영 복잡도, 비용 |

### 프로젝트 기본 방향
- Raspberry Pi에서는 버튼, 음성 입력, 장치 제어 등 Edge 기능을 우선 처리한다.

- 복합 요청 분석은 Backend에서 수행한다.

- 로컬 LLM과 클라우드 LLM은 동일한 테스트 발화로 비교한다.

- 모델 선택은 정확도뿐 아니라 응답 시간, 비용, 안정성, 개인정보 처리까지 함께 평가한다.

## 7. 구조화된 출력 형식

LLM의 응답을 바로 API에 전달하지 않고, 먼저 검증 가능한 구조로 변환한다.

### 예시 입력
> 9월 27일 오후 3시까지 보고서 검토해야 해. 2시간 전에 알려줘.

### 예시 출력
```
{
  "intent": "create_task",
  "task_name": "보고서 검토",
  "due_at": "2026-09-27T15:00:00+09:00",
  "reminder_before_minutes": 120,
  "priority": null,
  "needs_clarification": false,
  "clarification_question": null
}
```

### 출력 검증 규칙
- `intent`는 허용된 값 중 하나인지 확인한다.

- `task_name`은 비어 있지 않은지 확인한다.

- 날짜와 시간은 타임존을 포함한 표준 형식으로 변환한다.

- 필수 정보가 없으면 API를 호출하지 않는다.

- `needs_clarification`이 `true`이면 데이터 변경 없이 재질문한다.

- API 호출 결과를 확인한 후 최종 응답을 생성한다.

## 8. 요청 처리 정책

### 정상 요청
- 음성을 텍스트로 변환한다.

- Intent를 분류한다.

- 필요한 정보를 추출한다.

- 필수 값과 형식을 검증한다.

- 필요한 MCP Tool 또는 API를 호출한다.

- 실제 실행 결과를 확인한다.

- 사용자에게 결과를 안내한다.

### 불명확한 요청

대상 업무, 날짜, 시간 등 실행에 필요한 정보가 부족하면 임의로 실행하지 않는다.
> “어떤 보고서를 말씀하시는 건가요? ‘캡스톤 보고서’와 ‘클라우드 보고서’ 중 어떤 업무인가요?”

### 사용자 확인이 필요한 경우
- 동일하거나 유사한 업무가 여러 개 존재할 때

- 날짜 해석이 여러 가지일 때

- 기존 데이터의 중요한 값을 변경할 때

- 실행 대상과 변경 내용이 명확하지 않을 때

## 9. Fallback 및 오류 처리

| 상황 | 처리 방법 |
| --- | --- |
| STT 실패 | 음성 재입력 요청 |
| Intent 신뢰도 낮음 | LLM 분석 또는 사용자 재질문 |
| LLM Timeout | 제한 시간 초과 안내 및 재시도 선택지 제공 |
| 필수 정보 누락 | API 호출 없이 필요한 정보 질문 |
| MCP/API 실패 | 성공으로 안내하지 않고 실패 원인 또는 재시도 안내 |
| 네트워크 단절 | 요청 상태를 기록하고 연결 복구 후 재처리 검토 |
| 중복 요청 | `request_id`를 사용해 중복 실행 방지 |
| 모델이 근거 없는 값을 생성 | 출력 검증 후 사용자 확인 요청 |

## 10. 프롬프트 설계 초안

### System Prompt 기본 원칙
```
너는 업무관리 AI 데스크 펫의 요청 분석 모듈이다.

규칙:
1. 사용자의 요청에서 의도와 업무 정보를 구조화하여 추출한다.
2. 확인할 수 없는 정보를 임의로 생성하지 않는다.
3. 업무 대상이나 날짜가 불명확하면 재질문한다.
4. 데이터 변경 Tool은 필수 정보가 모두 확인된 경우에만 제안한다.
5. 실제 Tool 실행 결과를 확인하기 전에는 성공했다고 말하지 않는다.
6. 반드시 지정된 JSON 형식으로 응답한다.
```

### 프롬프트 작성 체크리스트
- 모델의 역할이 명확한가?

- 허용된 Intent 목록이 정의되어 있는가?

- 출력 JSON Schema가 고정되어 있는가?

- 날짜·시간 처리 기준이 있는가?

- 재질문 조건이 정의되어 있는가?

- Tool 호출 전 검증 조건이 있는가?

- 실패했을 때의 응답 방식이 있는가?

## 11. MCP와 LLM의 관계

LLM은 직접 업무 데이터를 변경하는 주체가 아니다. LLM은 사용자의 자연어 요청을 해석하고, 필요한 Tool과 매개변수를 제안한다. 실제 데이터 변경은 Backend의 검증을 거쳐 MCP 또는 Eureka Process API가 수행한다.
```
사용자 요청
    ↓
LLM: 의도·매개변수·필요 Tool 판단
    ↓
Backend: 권한·형식·필수값 검증
    ↓
MCP / Eureka Process API: 실제 실행
    ↓
Backend: 결과 검증
    ↓
LLM 또는 Backend: 사용자 응답 생성
```

## 12. 테스트 및 평가 기준

### 테스트 데이터 구성
- 업무 등록 발화

- 업무 조회 발화

- 업무 완료 발화

- 마감일 변경 발화

- 알림 시간 지정 발화

- 여러 업무가 존재하는 모호한 발화

- 날짜가 생략된 발화

- 네트워크 오류 상황

- API 응답 지연 상황

### 기록할 평가 항목

| 평가 항목 | 기록 내용 |
| --- | --- |
| Intent 정확도 | 의도를 올바르게 분류했는가 |
| 정보 추출 정확도 | 업무명·날짜·시간·우선순위를 정확히 추출했는가 |
| 재질문 정확도 | 불명확한 요청을 실행하지 않고 질문했는가 |
| Tool 선택 정확도 | 적절한 API 또는 MCP Tool을 선택했는가 |
| 응답 시간 | 발화 종료부터 첫 응답까지 걸린 시간 |
| 실행 안정성 | Timeout·네트워크 오류를 처리했는가 |
| 중복 실행 방지 | 같은 요청이 중복 처리되지 않았는가 |
| 응답 품질 | 짧고 이해하기 쉬운 문장인가 |
