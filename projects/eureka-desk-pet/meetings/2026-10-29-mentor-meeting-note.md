## 한줄 결론

사용자가 버튼을 누르고 말하면 **하드웨어는 녹음해서 백엔드로 넘기고, 백엔드가 STT·Gemini 분석·Eureka 호출을 모두 처리해
답변 문장과 표정을 돌려주는** 구조로 정리했다. 멘토는 하드웨어 부담이 작은 단순한 구조라 괜찮다고 봤다.
인터페이스는 **요청에서 `request_id`를 빼고 응답에만 두는** 쪽으로 바꾸기로 했고, **WebSocket 선제 알림은 1차에서 뺐다.**
하드웨어는 0·2번(김리윤)과 1번(김지훈), 백엔드는 API·Eureka·출력(이서현)과 의도 분석·재질문(박시현)으로 나눴다.
이번 주~다음 주에 각자 구현하고, 다음 주~다다음 주 사이에 하드웨어와 백엔드를 붙여 테스트한다.

## 핵심 내용

### 1. 팀 협업 방식

- 팀 회의는 매주 한다. **수요일은 필수, 화요일은 선택**(슬라이드 3). 지난주와 이번 주는 시험 기간이라 따로 모이지 않았다.
- 팀 회의에서는 멘토가 낸 과제를 서로 공유하고, 겹치는 작업을 조율하고, 외형처럼 의견이 필요한 부분을 정한다.
- 멘토 요청: **팀 회의 때 업무를 나누고, 팀장이 진행 상황을 확인**해 달라. 마감까지 한 달 정도 남아 일정이 빠듯하다.

### 2. 진행 상황

- **하드웨어**: LCD 패널, 오디오 앰프, 사각 스피커, 버튼, 3D 프린터 재료가 도착했다. **마이크 모듈만 남았다.**
  마이크가 없어도 LCD에 표정 띄우기, 버튼 입력·출력 테스트는 할 수 있다.
  (슬라이드 2에는 "부품 배송 기다리는 중"으로 적혀 있으나 회의 중 발언 기준으로 정리했다)
- **백엔드**(슬라이드 7): Eureka **등록·조회는 동작**한다. 완료·마감 수정은 Eureka 호출 함수만 있고 처리 흐름에 연결되지 않았다.
  `EUREKA_MODE=mock`이면 키 없이 메모리상의 가짜 Eureka로 개발할 수 있다. 프레임워크는 **FastAPI**.
- **AI**: Gemini 3.5로 "오늘 할 일 알려줘" 같은 요청을 10번 넣어 보니, 말한 뒤 동작이 실행되기까지 **중앙값 1.29초**가 나왔다.
  멘토는 다른 팀이 Gemini로 25초가 걸렸다고 들어 25초~1분 이상을 예상했는데 그보다 훨씬 빨랐다.
  측정 구간과 모델 이름은 § 판독 불확실 #2 참고.

### 3. 전체 흐름 (슬라이드 4)

멘토가 사용자 시나리오 순서대로 각 단계가 하드웨어에서 일어나는지 백엔드에서 일어나는지 물으며 정리했다.

1. 사람이 버튼을 누르고 말한다. 예: "나 다음 달에 시험 있어, 태스크 등록해 줘"
2. **하드웨어**가 말을 녹음해 그대로 백엔드로 보낸다.
3. **백엔드**가 음성을 텍스트로 바꾸고(STT), Gemini가 텍스트를 분석하고, Eureka API를 호출한다.
4. 백엔드가 사용자에게 들려줄 **문장과 표정 값**을 만들어 돌려준다.
5. **하드웨어**가 문장은 스피커로 읽어 주고(TTS), 표정은 LCD에 이미지로 보여 준다.

- 처음에 "LLM 연동과 하드웨어 연결이 안 돼 있다"는 말이 나왔는데, 멘토가 확인해 보니 **하드웨어가 LLM과 직접 연결될 일은 없고,
  백엔드가 LLM과도 하드웨어와도 아직 연결되지 않았다**는 뜻이었다.
- 멘토 판단: 구조가 단순하고 하드웨어에 부담이 적어 괜찮다.

### 4. LCD 표정과 외형

- 표정은 LED가 아니라 **LCD**로 보여 준다. 외형은 **레트로 컴퓨터** 콘셉트로 잡고 있다(김리윤이 화면 공유).
- 에러 등 상태별 표정 이미지를 멘토가 전에 적어 준 화면 크기에 맞춰 만들어 봤다. 아직 확정은 아니고 방향만 잡은 것이다.
- 결론: **백엔드가 표정 값을 보내면 하드웨어가 그 값에 맞는 이미지(또는 짧은 영상)를 띄운다.** 표정 그림은 나중에 바꾸면 된다.

### 5. 하드웨어–백엔드 인터페이스

멘토가 이서현·박시현에게 지난번 정의한 인터페이스를 그대로 쓰는지 확인했고, 슬라이드 4·5에 요청과 응답을 적어 함께 검토했다.

**요청** (하드웨어 → 백엔드, `POST /api/voice`)

```text
{ audio: 음성 파일, user_id }
```

- **`request_id`를 요청에서 뺀다.** 요청마다 붙는 고유 번호는 하드웨어가 만들 필요 없이 백엔드가 만들어 **응답에만** 넣는다.
- **`user_id`는 선택값**으로 둔다(슬라이드 7). Eureka는 API 키로 사용자를 구분하는데, 로그인은 구현 범위에 없다.
  → **로그인 없이 계정 하나로 쓰고, Eureka API 키는 백엔드 환경 변수에 둔다.** 팀도 이렇게 해도 괜찮다고 답했다.
- 하드웨어는 기기 토큰을 설정 파일에 들고 있다가 `X-Device-Token` 헤더로 보낸다(슬라이드 7).

**응답** (백엔드 → 하드웨어)

```text
{ id(=request_id), status, message, output: { tts, expression, text } }
```

| 필드 | 뜻 |
| --- | --- |
| `status` | 백엔드가 요청을 잘 처리했는지, 오류가 났는지 나타내는 코드. 표정과는 별개다 |
| `output.tts` | 스피커로 읽어 줄 문장 |
| `output.expression` | LCD에 띄울 표정 값 |
| `output.text` | 표정과 함께 LCD에 보여 줄 짧은 문구 (예: "업무 2건") |

- 멘토 결론: **이 형식으로 고정하고, 부품이 도착했으니 하드웨어는 이번 주에 이 형식으로 구현한다.**
- 요청 형식이 바뀌므로 백엔드가 정리한 최종본을 하드웨어에 다시 전달해야 한다(A5).
- 슬라이드에 적힌 초안(`expression`이 `output` 바로 아래, `statusCode` 404·500)과 현재 백엔드 실제 응답
  (`output.lcd.expression`, `status: "OK"`)의 모양이 다르다. 어느 쪽으로 맞출지는 § 판독 불확실 #3.

### 6. WebSocket 선제 알림은 1차에서 제외

- WebSocket은 **마감 임박 알림** 때문에 둔 것이다. 백엔드가 주기적으로 업무 목록을 확인하다가 마감이 가까우면 WebSocket으로 알린다.
- 결정: **선제 알림은 중요도가 낮아 1차에서 뺀다.** 하드웨어 작업 목록에서 WebSocket 관련 항목은 모두 빼고,
  백엔드 6번(선제 알림)은 여유가 있을 때 한다.
- 백엔드 현재 상태(슬라이드 7): WebSocket 연결(`/ws/hardware/{user_id}`)과 PING/PONG은 동작하고, 알림 메시지 형식도 정해져 있다.
  남은 일은 60초마다 Eureka 목록 조회해 마감 1시간 전 업무 찾기, `proactive_alert` 보내기, 못 보낸 알림 재전송, 서버 시작 시 자동 실행이다.

### 7. 하드웨어 작업 목록과 분담 (슬라이드 6)

| 번호 | 작업 | 담당 | 비고 |
| --- | --- | --- | --- |
| 0 | 부팅·대기: 하드웨어 초기화, 대기 상태 진입(LED 초록, LCD 기본 표정과 시계) | 김리윤 | 0-2 WebSocket 연결은 제외 |
| 1 | 음성 요청: 버튼 감지(GPIO17, 100ms 안에 반응) → 녹음(최대 15초) → 무음 확인 → 16kHz·16bit·모노 변환 → 백엔드 전송 → "생각 중" 표시 후 응답 대기 | 김지훈 | 녹음 시작만 마이크가 필요하다. 나머지는 **음성 파일을 넣어 두고** 먼저 테스트한다 |
| 2 | 응답 출력: 응답의 `tts`·`expression`·`text`를 받아 말하는 상태로 전환 → TTS 재생 → 대기 상태로 복귀 | 김리윤 | 재질문 응답이면 재생 후 버튼 입력을 기다린다 |
| 3 | 선제 알림 | — | **1차 제외** |
| 4 | 예외 처리: 네트워크 끊김, 응답 시간 초과·오류 수신 | 각 담당 | 0·1·2번을 맡은 사람이 각자 자기 부분에서 처리한다 |

- 분담은 멘토가 0·2번과 1번으로 나누자고 제안했고, 김지훈이 1번을 맡겠다고 해서 정했다.
- 다음 주까지 할 항목은 슬라이드에 두 사람이 배경색으로 표시하기로 했다.
- 슬라이드에는 응답 출력 때 **서보 모터로 고개를 움직이는 동작**도 적혀 있다. 지금 계약(`contracts.md` § 5)에는 없는 항목이다.

### 8. 백엔드 작업 목록과 분담 (슬라이드 7)

| 번호 | 작업 | 담당 | 상태 |
| --- | --- | --- | --- |
| 1 | 요청 수신·검증: 기기 토큰 확인(틀리면 401), WAV 형식 검사(아니면 422), 15초·1MB 초과 거절(413). 시연용 `POST /api/text`도 있음 | 이서현 | — |
| 2 | 음성 인식·의도 분석: Gemini 3.5 Flash-Lite **1회 호출**, temperature 0.1, JSON만 출력. 현재 시각·미완료 업무 30개·직전 재질문을 함께 넣음. action 6종 | 박시현 | — |
| 3 | Eureka 업무 처리: 등록·조회 동작, 완료·마감 수정은 흐름 연결 전. 정책 검증은 코드에서 강제 | 이서현 | 일부 동작 |
| 4 | 재질문: 이름·마감 누락, 지난 마감, 0분 이하 알림, 대상 업무가 없거나 여럿일 때. 원래 요청은 `user_id`별로 60초 보관 | 박시현 | **이번 주** |
| 5 | 출력 생성: `tts`와 표정·문구를 템플릿으로 만듦(LLM 재호출 없음). 전체 9초 제한, LED 색은 보내지 않음 | 이서현 | — |
| 6 | 마감 임박 선제 알림 | — | 여유 있을 때 |

- 멘토 제안: 1번 요청이 들어오면 2~4번이 그 안에서 한 번에 돌고 5번이 응답이 된다. **만들 API는 사실상 하나**다.
  → 이서현은 **입출력을 하드코딩해서라도 클라우드에 API 하나를 먼저 열어** 하드웨어가 바로 붙어 작업할 수 있게 한다.
  클라우드(AWS) 배포도 이번 주에 한다.
- 이서현과 박시현은 같은 API 안에서 작업하므로 **두 사람 사이의 함수 입출력도 꼼꼼하게 정리**해 둔다.

### 9. 일정

- 하드웨어·백엔드 모두 남은 양이 많지 않다고 멘토가 판단했다. **이번 주~다음 주에 각자 구현을 끝내고,
  다음 주~다다음 주 사이에 둘을 연동해 테스트**한다.
- 팀 회의 때 이 슬라이드를 보며 진행 상황을 점검한다. 이슈가 생기면 따로 공유한다.
- 작업한 코드와 문서는 GitHub와 knowledge vault에 올린다.
